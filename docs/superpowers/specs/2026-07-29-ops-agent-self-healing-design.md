# 运维智能体：自愈执行链设计

**日期：** 2026-07-29
**状态：** 已实施，已验证

## 目标

在已经完成的权限、审计和智能诊断基础上，将运维智能体升级为保守通用型自愈助手。用户描述故障后，智能体应自动采集证据、生成可审查的修复计划、按权限执行用户批准的步骤，并在每一步后自动复查结果。

用户不需要复制命令到终端。所有诊断、修复和验证命令都由软件通过当前 SSH 连接执行；需要授权时只让用户确认是否执行。

## 范围

本阶段覆盖四类通用运维问题：

- 服务异常：服务未运行、重启失败、最近日志报错。
- 磁盘空间不足：磁盘或 inode 使用率过高、可安全清理的缓存或日志过大。
- 进程异常：CPU 或内存占用异常、僵尸进程、重复进程。
- 网络端口异常：预期端口未监听、端口被占用、连接状态异常。

本阶段不处理账户、SSH 登录策略、防火墙清空、磁盘格式化、分区调整、递归删除、数据库删除等高风险修复。遇到这类问题时，智能体只能报告风险和建议人工专项处理；如果后续阶段要支持，仍必须经过现有高风险二次确认机制。

## 方案选择

采用“计划驱动的保守自愈”。

- 不采用完全自动修复，因为用户是非专业运维人员，错误修复的代价高。
- 不采用只做普通聊天建议，因为用户明确希望全自动执行，不希望手动运行命令。
- 推荐方案是在智能体和 SSH 执行之间增加结构化修复计划层：计划可解释、可审计、可逐步执行，也能自然扩展到后续多机编排。

## 自愈工作流

一次自愈流程分为六个阶段：

1. **确认上下文**：确认当前 SSH 会话、主机名称和连接状态；未连接时停止并提示先连接主机。
2. **采集证据**：自动执行有界只读诊断命令，复用现有健康、磁盘、进程、网络和日志诊断能力。
3. **生成计划**：把证据转为 `RemediationPlan`，每个步骤都包含目的、命令、风险、验证命令和停止策略。
4. **用户审查**：在聊天区展示自愈计划卡片。只读验证可自动执行；变更步骤使用现有权限策略弹确认；高风险仍二次确认。
5. **执行步骤**：每一步执行前都调用 `opsAgentStore.decide()` 和统一授权回调，禁止直接调用 SSH。
6. **自动复查**：每个变更步骤执行后立即运行验证命令；验证失败时停止后续变更，把输出交给智能体重新分析。

## 数据模型

新增自愈领域类型，保持为纯 TypeScript 数据结构，方便测试和后续多机扩展。

```ts
export type RemediationStepStatus =
  | 'pending'
  | 'waiting_approval'
  | 'running'
  | 'verifying'
  | 'completed'
  | 'failed'
  | 'skipped'

export interface RemediationEvidence {
  source: string
  summary: string
  severity: 'info' | 'warning' | 'critical'
}

export interface RemediationStep {
  id: string
  title: string
  goal: string
  command: string
  verifyCommand: string
  expectedResult: string
  risk: CommandRisk
  stopOnFailure: boolean
  status: RemediationStepStatus
  auditId?: string
  outputSummary?: string
  verificationSummary?: string
}

export interface RemediationPlan {
  id: string
  hostId: string
  hostName: string
  issueType: 'service' | 'disk' | 'process' | 'network' | 'unknown'
  title: string
  evidence: RemediationEvidence[]
  steps: RemediationStep[]
  createdAt: number
  status: 'draft' | 'ready' | 'running' | 'completed' | 'failed' | 'stopped'
}
```

`verifyCommand` 是必填字段。没有验证命令的变更步骤不得进入可执行计划。

## 用户界面

现阶段不新增复杂页面，先嵌入右侧 AI 智能体。

- 顶部继续显示权限档位按钮和审计按钮。
- 聊天消息中新增自愈计划卡片，展示问题类型、证据摘要、步骤列表和整体状态。
- 每个步骤展示步骤名称、风险标签、执行命令、验证命令、当前状态和简短输出摘要。
- 卡片提供“执行计划”和“停止计划”操作；执行时逐步触发现有权限确认。
- 如果用户拒绝某一步，默认停止计划，避免后续步骤依赖未完成的前置修复。

界面文案保持克制，重点告诉用户“系统准备做什么、为什么、风险是什么、如何验证”，不要求用户理解复杂 shell 细节。

## 安全边界

- 自愈流程必须复用现有命令权限策略和审计 store，不能直接调用 SSH。
- 高风险命令始终二次确认，自定义规则也不能把高风险降为自动执行。
- 变更步骤必须有验证命令；验证命令优先使用只读命令。
- 诊断证据不足时，只能追加只读诊断，不能猜测并执行修复命令。
- 命令超时、SSH 断开、非零退出码和空输出都必须写入步骤状态和审计摘要。
- 任一变更步骤失败后，默认停止后续变更，让智能体基于失败输出重新分析。
- 模型输出的修复计划需要经过本地解析和策略检查；解析失败时降级为普通聊天说明，不执行任何命令。

## 错误处理

- **SSH 断开**：使用既有连接重试机制；仍失败则停止计划。
- **命令被策略拒绝**：步骤标记为 `skipped`，计划标记为 `stopped`。
- **用户取消确认**：步骤标记为 `skipped`，计划标记为 `stopped`。
- **执行失败**：步骤标记为 `failed`，保存脱敏输出摘要，并停止后续变更。
- **验证失败**：步骤标记为 `failed`，保存验证摘要，并停止后续变更。
- **AI 计划格式不合法**：不执行命令，提示智能体重新生成计划或转为普通诊断说明。

## 测试与验证标准

- 添加自愈计划解析与校验测试：变更步骤缺少 `verifyCommand` 时必须被拒绝。
- 添加执行链回归测试：自愈步骤必须通过统一授权回调，不能直接导入或调用 SSH 执行器。
- 添加失败停止测试：变更步骤执行或验证失败后，不得继续执行后续变更步骤。
- 添加安全测试：计划中出现固有高风险命令时，必须保持二次确认，不得自动执行。
- 运行现有 `test:agent-execution`、`test:ops-permissions`、前端构建、Rust 检查，并实际启动桌面应用检查启动错误。

## 后续扩展

第三阶段多机编排应复用 `RemediationPlan` 和 `RemediationStep`，把单主机计划扩展为多主机计划集合。并发、灰度、失败回滚和结果汇总属于第三阶段，不在本阶段实现。

## 设计自审

- 本设计聚焦单主机自愈执行链，没有混入多机编排。
- 所有执行命令都经过现有权限策略和审计记录，避免绕过第一阶段安全边界。
- 变更步骤必须带验证命令，确保修复不是只执行不复查。
- 文档没有未定占位、未说明的自动执行路径或互相矛盾的权限规则。
