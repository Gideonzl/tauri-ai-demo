# SSH 会话健康与无感恢复设计

## 目标

让长时间空闲、网络短暂中断或应用重新获得焦点后的 SSH 终端能够自动恢复，避免用户遇到“终端看似已连接但无法继续输入”的情况。恢复过程遵循极简原则：正常状态不增加控件，只有恢复持续超过 1 秒或最终失败时才显示必要信息。

## 范围

本阶段包含：

- 为每个前端 SSH 会话维护结构化健康状态。
- 将 Rust SSH/PTY 状态事件同步到 Pinia 会话状态。
- 在窗口重新激活或会话长时间空闲后执行轻量健康检查。
- 异常时自动重建 SSH transport 与 PTY，并保留原终端标签。
- 自动恢复失败后提供紧凑的手动“重新连接”入口。
- 增加自动化回归测试并检查应用启动错误。

本阶段不包含：

- 新增独立的健康监控页面。
- 固定频率执行远程 Shell 命令。
- 保存长期会话健康历史或上传遥测数据。
- 更改服务器认证资料、权限模型或脚本业务。
- 打包 Windows 安装程序。

## 现状与问题

当前 Rust 后端已经具备以下能力：

- 每 15 秒发送 SSH keepalive，最多容忍 4 次丢失。
- PTY 收到 EOF/Close 后发出 `reconnecting` 状态。
- 用户输入写入失败时，重建 SSH transport 和 PTY 后重试一次输入。
- PTY 写入带 5 秒确认超时，非交互命令通道也有超时保护。

目前缺口是：

- `SSHShellSession` 收到后端状态后没有完整更新 Pinia 会话对象。
- 前端不能区分“健康、检查中、恢复中、恢复失败”等状态。
- 半开连接通常要等用户输入后才暴露，首个输入可能出现明显等待。
- 自动恢复失败后缺少不会干扰终端内容的重试入口。
- 恢复次数、原因、最后活动时间等诊断信息没有结构化保存。

## 方案选择

采用混合恢复方案：复用现有 keepalive 和输入时兜底恢复，同时在应用重新获得焦点或长时间空闲后做一次轻量探测。探测仅验证 SSH channel，不执行用户 Shell 命令，不产生终端输出。

未采用的方案：

- 仅在输入时恢复：实现简单，但半开连接会让首个输入等待超时。
- 固定频率远程探测：状态更及时，但会持续创建远程 channel，增加服务器和客户端负担。

## 会话健康模型

扩展前端 `SshSession`，增加可选健康字段，避免破坏现有调用方：

```ts
type SshHealthState = 'healthy' | 'checking' | 'recovering' | 'failed'

interface SshSessionHealth {
  state: SshHealthState
  lastActivityAt: number
  lastCheckedAt?: number
  recoveryStartedAt?: number
  recoveredAt?: number
  reconnectCount: number
  reason?: string
}
```

规则：

- SSH 连接和 PTY 建立成功后为 `healthy`。
- 收到或发送终端数据时更新 `lastActivityAt`。
- 轻量检查期间为 `checking`，检查成功后回到 `healthy`。
- 后端发出 `reconnecting` 或检查失败并开始重建时为 `recovering`。
- 所有自动恢复尝试失败后为 `failed`。
- 成功恢复时递增 `reconnectCount`，记录 `recoveredAt` 并清除失败原因。
- 会话健康数据只存在内存中，不写入本地服务器配置。

## 后端能力

新增幂等的会话检查/恢复接口，职责保持分离：

1. `ssh_check_session`
   - 使用短超时打开一个 SSH session channel。
   - 不执行远程 Shell 命令，不写入终端输出。
   - 成功后立即关闭 channel。
   - 半开、超时或 channel 打开失败时返回结构化错误。

2. `ssh_recover_session`
   - 对同一 `sessionId` 使用单任务锁，多个调用共享同一次恢复结果。
   - 使用会话中已有认证配置重新建立 transport。
   - 使用保存的终端尺寸重建 PTY。
   - 成功后继续沿用原 `sessionId` 和终端标签。
   - 通过现有 `ssh-status` 事件发送 `reconnecting`、`connected` 或 `error`。

现有 `ssh_write` 的失败重试继续保留，作为最后一道兜底。恢复过程不得清空前端终端缓冲区，也不得静默切换到 DemoSession。

## 前端协调

`SSHShellSession` 负责后端通信和串行化：

- 暴露状态回调和活动回调，供 `TerminalPanel` 更新 Pinia。
- 所有检查、恢复和用户输入通过同一条异步队列协调。
- 同一会话同时只能有一个检查或恢复任务。
- 恢复期间到达的用户输入排队等待，恢复成功后按原顺序发送。
- 组件销毁或标签关闭后，未完成任务不得继续更新已关闭会话。

`TerminalPanel` 负责界面映射，不自行实现连接协议：

- 后端状态事件实时更新该面板对应的 Pinia 会话。
- 页面重新获得焦点时，如果距离最后活动超过 60 秒，则触发一次检查。
- 检查成功不显示消息。
- 检查失败自动进入恢复流程。
- 手动重连只调用同一个恢复入口，不复制另一套逻辑。

## 极简交互

正常状态：

- 终端顶部只保留绿色状态点。
- 不显示“健康”、延迟、计数或额外按钮。

检查状态：

- 检查在 1 秒内完成时不改变界面。
- 检查超过 1 秒才显示“正在检查连接…”。

恢复状态：

- 恢复持续超过 1 秒时，在现有终端顶部状态区域显示“正在恢复连接…”。
- 不使用模态框，不向终端正文插入重复日志，不遮挡输入区域。

恢复成功：

- 显示“连接已恢复”约 2 秒，然后回到仅绿色状态点。
- 保留终端滚动内容、标签位置、当前选择和终端尺寸。

恢复失败：

- 状态点变为错误色。
- 顶部状态区域显示失败摘要和紧凑的“重新连接”文字按钮。
- 点击后调用幂等恢复入口；不要求用户重新创建服务器或手动执行命令。

## 错误处理

- 健康检查使用短超时，不能无限等待。
- 自动恢复最多执行两轮，第二轮采用短暂退避，避免瞬时网络抖动导致直接失败。
- 认证失败、服务器配置缺失或会话已删除时不循环重试。
- 多标签会话完全隔离，一个标签恢复不能改变其他标签状态。
- `ssh-status` 事件缺少可选字段时保持兼容，使用现有状态字符串作为最低保障。
- 前端状态更新失败不得阻断原始终端数据和键盘输入链路。

## 数据流

```text
窗口重新激活 / 长时间空闲
  -> TerminalPanel 请求健康检查
  -> SSHShellSession 串行队列
  -> ssh_check_session
  -> 成功：更新 healthy（无 UI 打扰）
  -> 失败：ssh_recover_session
  -> Rust 重建 transport + PTY
  -> ssh-status(reconnecting/connected/error)
  -> TerminalPanel 更新 Pinia 健康状态
  -> 超过 1 秒才显示恢复提示

用户输入
  -> SSHShellSession 输入队列
  -> ssh_write
  -> 写入失败：Rust 原有恢复逻辑重建并重试一次
  -> 输入按原顺序送达，或进入 failed 并显示重连入口
```

## 测试与验收

自动化测试至少覆盖：

- 健康状态的合法转换和时间字段更新。
- 60 秒以内重新激活不触发检查，超过阈值只触发一次。
- 检查失败后自动恢复，成功后回到 `healthy`。
- 连续触发检查/恢复时保持单任务执行。
- 恢复期间输入排队并在成功后按顺序发送。
- 自动恢复失败后进入 `failed`，手动重连复用同一入口。
- 后台标签的事件只更新自身状态。
- 恢复过程不清空终端、不创建 DemoSession、不丢失标签顺序。
- 中英文状态文案均存在且暗色/亮色主题可读。

完成后执行：

- 新增会话健康专项测试。
- 现有 SSH 终端可靠性测试。
- 现有终端布局、标签排序、操作记录和数据管理回归测试。
- TypeScript/Vite 构建。
- Rust 检查或测试。
- 启动开发服务，确认无启动报错和错误覆盖层。

## 完成标准

- 空闲或网络短暂中断后，用户无需手动执行命令或重新创建连接。
- 正常连接时界面不增加常驻按钮和文字噪声。
- 恢复超过 1 秒才出现状态提示，失败后才出现重连入口。
- 原标签、终端内容、输入顺序和多会话隔离均得到保留。
- 所有专项测试、回归测试、构建和启动检查通过。
